# Phase V2-3 – Multi-language (Dutch + English)

Status: ✅ done (1.3.0)

## Goal
The whole UI and all notifications available in Dutch and English, chosen per user. Also the readme should be translated. All info should be found in the general readme.

## Decisions (from Q&A)
- Languages: **nl** (default) and **en**.
- Chosen **per user** in Profiel and stored on the server, so it follows the user to every device.
- First default (no choice yet): browser language (`navigator.languages`) if it starts with `en`,
  otherwise Dutch. Login screen (not logged in yet): browser language, remembered per device.
- **Push notifications** and server-generated texts use the **recipient's** language.
- User content (step titles/texts, travel names, comments, custom stat labels) is never translated.

## Tasks

### Web
- Move `web/src/i18n/nl.ts` to `i18n/locales/nl.ts`; add `i18n/locales/en.ts` typed as
  `Messages = typeof nl` so a missing English key is a **type error**.
- `I18nProvider` + `useT()` hook; replace the direct `nl` imports (≈34 files).
- Locale-aware formatting in `lib/format.ts`: `nl-NL` / `en-GB` for dates, numbers and relative
  times. Units stay **metric** in both languages.
- `<html lang>` follows the language; TipTap editor labels, photo picker, map popups, confirm
  dialogs, install banner and iOS instructions translated.
- Language switch in Profiel (and on the login screen as a small toggle).
- Server error messages: the client shows a translated text based on the error `code`
  (`HttpError` already has one); the server message is only a fallback.

### Server
- Migration: `users.language TEXT NULL` ('nl' | 'en'; NULL = not chosen yet).
- `GET /api/auth/me` returns `language`; `PATCH /api/profile` accepts it.
- Notification texts (`notifications/service.ts`) built from a small server-side message table per
  language, using the recipient's `language` (NULL → nl).
- Share page (V2-5) uses the visitor's browser language (no user).

### Shared
- `Language` type + supported list in `@travelsteps/shared`.

### Docs (decision 2026-10-22)
- All content of `code/README.md` moves to the root `README.md` (English) + a Dutch copy
  `README.nl.md` (linked to each other). `code/README.md` becomes a short pointer (Home Assistant
  shows it). References to `code/README.md` in `Analysis/**` and the requirements point to the root.

## Implementation plan
1. Shared: `LANGUAGES`, `Language`, `languageSchema`; `updateProfileSchema` → `displayName` and
   `language` both optional (at least one); `PublicUser.language: Language | null`.
2. Server: migration `ALTER TABLE users ADD COLUMN language TEXT`; repository/`toPublicUser`;
   `PATCH /api/profile` stores it; `notifications/messages.ts` (nl/en table) used per recipient.
3. Web: `i18n/locales/{nl,en}.ts` (`Messages = typeof nl`), `i18n/index.tsx` with
   `I18nProvider`, `useT()`, `useLanguage()`, module getter `t()` for non-React modules,
   `<html lang>`, localStorage per device; `format.ts` uses the current locale; error texts by
   `code` (`errors.codes`), server message as fallback (Dutch VALIDATION details are kept for nl,
   generic text for en – the forms validate in the browser first).
4. Language switch in Profiel (saved on the server; offline: kept locally and sent when online)
   and a small NL/EN toggle on the login screen.
5. READMEs, version 1.3.0, changelog, requirements.
6. Tests: key-completeness (web), server tests for `language` on me/profile and push texts.

All tasks done (Share page: V2-5 still to come; it will use the browser language).

## Compatibility
- Existing users have `language = NULL` → browser default → Dutch for most; nothing changes for them
  until they choose.
- API only gets an extra field; old clients ignore it.
- Offline: all locale files are bundled in the precache, so switching language works offline (the
  choice syncs when online).
- Phase V2-1 wording ("stap") is the Dutch base; English uses "step".

## Acceptance criteria
- Switching to English translates every screen, dialog, toast, empty state and push notification;
  no Dutch left (spot-check + key-completeness type check).
- Dates/numbers formatted per language; units metric.
- Language choice persists across devices and after re-login.
- Typecheck, lint, tests and build pass; unit test that `en` and `nl` have the same keys.

## Solution
- Hand-written i18n (no library): `i18n/store.ts` (module language + `messages()`), `i18n/index.tsx` (`I18nProvider`, `useT`, `useLanguage`, `useChooseLanguage`), `locales/{nl,en}.ts` with `en: Messages`.
- Language on `users.language` (migration), returned by `/api/auth/me`, set via `PATCH /api/profile`; offline choice kept in localStorage and sent when online.
- Push texts from `server/src/notifications/messages.ts` per recipient language (NULL → nl).
- Deviations: route URLs, PWA manifest description and admin service details (server texts) stay Dutch; shared zod messages are Dutch (English shows the code-based text).
